# Тести з критеріїв приймання

Вхід: список історій, напр. `US-05 US-07 US-12`.
Рівні, іменування, ізоляція й тестові дані — за `docs/testing-strategy.md`. Правила проєкту — `AGENTS.md`.

## 1. Спершу вимоги, потім код

Прочитай Gherkin-сценарії цих історій у `docs/requirements.md` §4 і потрібні частини `docs/api.md` (коди помилок, поля знімка) та `docs/tiles.md`.
Код продукту на цьому кроці не відкривай.

## 2. Матриця

Склади таблицю:

| Сценарій | Рівень (game / room / httpapi / web / вручну) | Назва тесту | Очікуване значення | Звідки значення |
|---|---|---|---|---|

- «Звідки» — AC, `api.md`, `tiles.md` або ручний розрахунок за правилом (запиши розрахунок).
- Сценарії, які перевіряються лише очима (вигляд, мишка, буфер обміну, клавіатура), — «вручну». Не імітуй їх тестом.
- Окремо додай негативні випадки, які випливають з `api.md`, але не мають сценарію в AC.

Запиши матрицю в `docs/testing-report.md` → «Журнал: матриця покриття» і переходь до наступного кроку без підтвердження.

## 3. Код — лише для сигнатур

Тепер відкрий код, але бери з нього тільки публічні функції, типи й конструктори.
Якщо очікуване значення можна дізнатися лише з коду, а не з вимог, — це прогалина вимог. Запиши її, не вигадуй значення.

## 4. Напиши тести

Крім правил зі стратегії:
- Кожен сценарій з матриці — окремий підтест; успішний шлях і всі граничні випадки та помилки.
- Негативний випадок перевіряє **і** код помилки з `api.md`, **і** те, що стан не змінився (тайли, `deckCount`, поточний гравець, фаза, список гравців).
- Тільки справжні `game`, `room`, `store`. Моки й заглушки власних пакетів заборонені.
- Не обчислюй очікуване тією самою функцією, яку тестуєш (напр. не отримуй очікувані сегменти через `game.Rotate`). Очікуване записуй літералом.
- Перед циклом по результату перевір його довжину: цикл по порожньому зрізу не повинен давати «зелений» тест.
- Помилки на кроці підготовки (`Join`, `Connect`, `start_game`) перевіряй, а не ігноруй. Без `t.Skip`.

## 5. Запусти `npm test` і розбери падіння

Для кожного червоного тесту перечитай сценарій:
- **помилився тест** (неправильно прочитано AC) — виправ тест і поясни, що саме було не так;
- **помиляється код** — **не змінюй очікуване значення і не виправляй код.** Залиш тест червоним і допиши рядок у `docs/testing-report.md` → «Журнал: знайдені баги»:
  `сценарій | очікувано | фактично | ймовірна причина (файл:рядок)`.

## 6. Зламай код навмисно

Для кожної історії вибери 2–3 умови, від яких залежить сценарій. Приклади: порівняння сторін при стикуванні, перевірка наявності сусіда, перевірка активного гравця, межі 2–5 гравців, зменшення стопки, фільтр підсвітки за обертанням.

По одній мутації:
1. зміни умову (`==` → `!=`, `>=` → `>`, прибери перевірку);
2. запусти тести пакета;
3. запиши, який тест упав;
4. поверни файл: `git checkout -- <файл>`.

Якщо жоден тест не впав — тест слабкий. Посиль його й повтори мутацію.
Після всіх мутацій `git diff` для коду продукту має бути порожнім.

Результат допиши в `docs/testing-report.md` → «Журнал: зламай код навмисно»:
`файл:рядок | мутація | тест, що впав / «вижила» → що посилено`.

## 7. Підсумок у відповіді

- матриця покриття з фінальними назвами тестів;
- червоні тести і їх ймовірна причина;
- мутації, які вижили, і що зроблено;
- прогалини вимог.

Не комітити — коміти робляться після аудиту (prompts/6.3).
