# 6.0 Наступний інкремент MVP: «Зіграти хід» (US-05–US-12, US-14–US-16)

Інструмент: Claude Code (CLI-агент) у репозиторії. Агент сам читає `CLAUDE.md` → `AGENTS.md`, тому правила, стек і заборони тут не повторюються.

**Скоуп:** US-05, US-06, US-07, US-08, US-09, US-10, US-11, US-12, US-14, US-15, US-16 — партія стартує, гравці по черзі тягнуть, обертають і кладуть тайли, усі бачать ходи наживо.
**Поза інкрементом:** US-13 (міпли) і підрахунок US-18–US-23. Вони потребують обчислення об'єктів (Feature, обхід графа) і пишуться тестами першими за принципом з README, тому йдуть наступним інкрементом.

## Промпт 1. План і рішення щодо контракту

```text
Наступний інкремент MVP — сценарій «зіграти хід без міплів»: US-05, US-06, US-07, US-08, US-09, US-10, US-11,
US-12, US-14, US-15, US-16 з docs/requirements.md. US-13 і підрахунок очок (US-18–US-23) — наступний інкремент.

Перед кодом:
1. Прочитай AGENTS.md, docs/api.md, docs/data-model.md, docs/technical-analysis.md, docs/adr/0002-ui-stack.md
   і Gherkin-сценарії цих історій.
2. Склади список файлів, які створиш або зміниш, по шарах:
   game (новий пакет, без залежності від room, httpapi і мережі) → room → httpapi → web/src/api → web/src/game (чисті функції) → web/src/pages.
3. Знайди прогалини контракту, сам ухвали рішення для кожної і внеси його в docs/api.md
   (це і є згода на зміну контракту в сенсі AGENTS.md §7 — підтвердження не чекай). Щонайменше:
   - як клієнт дізнається, що тайл автоматично скинуто (US-09: «Тайл неможливо покласти, береться новий») — у room_state такого поля немає;
   - що відбувається, коли скінчилася стопка, поки підрахунку немає (моя пропозиція: FINISHED і finalScores з нулями, позначено shortcut до US-21–US-23);
   - тексти помилок ILLEGAL_PLACEMENT (зайнята клітинка / немає сусідів / сторони не збігаються — з AC US-12), NOT_YOUR_TURN, WRONG_PHASE;
   - що бачать гравці, коли партію перервано (ABANDONED);
   - як відповідати на place_meeple, поки US-13 не реалізовано.
   Кожне рішення коротко поясни у відповіді — не вигадуй поля мовчки.
4. Працюй у поточній гілці — її вже створено для цієї практики. Нових гілок не створюй.

Правило на весь інкремент: тести для нових історій генеруємо окремо з критеріїв приймання
(prompts/6.2_test_generation.md), щоб тести не повторювали код. Виняток — US-12: за AGENTS.md §6 її тест пишеться
першим (у кроці з пакетом game). Наявні тести мають лишатися зеленими. Історії інкременту не називай готовими за DoD (AGENTS.md §8),
доки 6.2–6.3 не закриють їх тестами й ручною перевіркою.
Після кожного кроку з кодом — go vet, go test, gofmt -l з виводом.

Код у цьому кроці не пиши — лише план і зміни в docs/api.md.
```

## Промпт 2. Каталог тайлів (зупинка на звірку з фізичною копією)

```text
Створи docs/tiles.md — каталог типів тайлів базової гри (A…X) у форматі TileType з docs/data-model.md:
id, count, isStart, segments (type, points, pennant, adjacentCities).
- Сума count = 72, рівно один стартовий екземпляр.
- Біля кожного типу — опис словами («місто на півночі, дорога схід–захід, щит»), щоб команда могла звірити його з коробкою.
- adjacentCities заповни вже зараз: вони знадобляться для US-22.
Також згенеруй docs/tiles-preview.html — самодостатню сторінку без залежностей, яка малює кожен тип схематично
(місто, дорога, поле, монастир, щит) з id і кількістю, дані — рівно з docs/tiles.md. Її відкриють поруч із коробкою.
Коду гри не пиши. Після файлів зупинись: команда звірить кожен тип і кількість із фізичною копією.
```

> **Звірку робимо вручну:** відкриваємо `docs/tiles-preview.html` і порівнюємо кожен тип, кількість і щити з коробкою. Кожну розбіжність записуємо: це реальні знахідки для розділу «Баги» в `docs/testing-report.md`.

## Промпт 3. Пакет game

```text
docs/tiles.md звірено з фізичною копією. Виправлення: <перелік або «немає»>.

Реалізуй server/internal/game — чисту логіку без мережі й без room.
Спершу тест першим для US-12 (AGENTS.md §6): табличний тест у game за Gherkin US-12 («Розміщення на допустиму позицію»,
«Недопустима позиція», «Клітинка без сусідів») плюс зайнята клітинка; поле — з типів docs/tiles.md, очікуване — літералами.
Покажи червоний вивід, потім код:
- каталог тайлів рівно з docs/tiles.md; перевірка інваріантів каталогу (сума 72, сегменти покривають 12 точок країв без перетинів);
- обертання сегментів на 0/90/180/270 за годинниковою стрілкою;
- стикування за правилом з docs/data-model.md (N0↔S2, N1↔S1, N2↔S0, так само E↔W, з урахуванням обертання);
- допустимі позиції тайла в усіх 4 обертаннях (US-11): клітинка вільна, має хоча б одного сусіда, усі сусідні сторони збігаються;
- стопка з 71 тайла; перемішування з джерела випадковості, яке передається ззовні (у тестах — фіксоване seed);
  автоматичне скидання тайла, який нікуди не лягає, і взяття наступного (US-09);
- стан партії: тайли на полі, поточне місце, фаза PLACE_TILE / PLACE_MEEPLE, номер ходу.
```

## Промпт 4. Кімната і WebSocket

```text
Підключи game до room і httpapi за планом з кроку 1: start_game (US-05), place_tile (US-12), skip_meeple (US-14)
і room_state.game — поведінка, коди помилок і поля рівно з docs/api.md (з ухваленими змінами). Окремо:

```

## Промпт 5. Клієнт

```text
Клієнт для того ж інкременту, без нових залежностей: types.ts рівно з docs/api.md; кнопка старту в Lobby і екран гри
за AC US-05…US-16 (написи й тексти — дослівно з AC; табло рахунку з 0 на старті). Рішення, яких в AC немає:
- поле на SVG (ADR-0002); тайли малюються схематично із сегментів каталогу, без завантажених зображень;
- клік по вільній клітинці надсилає place_tile, а текст помилки береться з відповіді сервера; клієнт сам не перевіряє стикування,
  підсвітка береться з legalPlacements;
- логіку, яку можна перевірити без браузера (наступне обертання; які клітинки підсвітити для обертання і гравця),
  винеси в чисті функції в web/src/game/ — для них будуть Vitest-тести.

Після коду: npm --prefix web run build, npm --prefix web run lint; підніми сервер і перевір, що /api/health відповідає, а головна віддає нову збірку
(окремого URL для гри немає: екран обирає web/src/App.tsx).
У браузері вручну перевірятиме команда (smoke-чекліст у 6.3) — не стверджуй, що зіграв у браузері, якщо не робив цього.
```

## Що закладено в промпти і чому

| Елемент | Навіщо |
|---|---|
| Скоуп «хід без міплів», US-13 і підрахунок — окремо | Інкремент видно на демо, а найризиковіша логіка (об'єкти й очки) не пишеться поспіхом без тестів |
| Перелік відомих прогалин контракту в плані; рішення — в `api.md` з поясненням | Скидання тайла, кінець стопки й ABANDONED не описані в `api.md`; без підказки агент вигадує поля мовчки. Рішення ухвалює агент, але записує їх у контракт, тож їх видно на рев'ю |
| Зупинка після `docs/tiles.md` на звірку з коробкою, сторінка-превʼю | Склад тайлів — те, що ШІ найімовірніше «згадає» неправильно; AGENTS.md забороняє його вигадувати. Картинку звірити з коробкою швидше, ніж таблицю сегментів |
| `game` без залежності від room і мережі | Логіку правил можна тестувати модульно (принцип 1 з README) |
| Джерело випадковості ззовні | Стопку й порядок ходів можна відтворити в тестах |
| Глибока копія знімка | Закриває shortcut з US-04: з появою Game знімок інакше читається поза м'ютексом — гонка даних |
| Тести для нових історій — в 6.2, крім тесту першим для US-12 | Тести генеруються з критеріїв приймання, а не з щойно написаного коду, тож не закріплюють його баги; US-12 за AGENTS.md §6 тестується до коду |
| Чисті функції в `web/src/game/` | Клієнтську логіку (обертання, підсвітка) можна перевірити без браузера |
| «Не стверджуй, що зіграв у браузері» | CLI-агент не клікає по сторінці; без заборони він звітує про перевірку, якої не було |
