# 6.3 Аудит якості тестів, виправлення багів і звіт

Інструмент: Claude Code, **нова сесія** (`/clear`). Аудитор не повинен бачити, як писалися код і тести: інакше він перевіряє сам себе.
Результат: виправлення з регресійними тестами, [`docs/testing-report.md`](../docs/testing-report.md), оновлений README.

## Промпт 1. Аудит (нічого не змінювати)

```text
Дій як скептичний QA-рев'юер, який не писав ні коду, ні тестів. Твоя задача — знайти, де тести брешуть або чогось не бачать.
Нічого не змінюй — лише звіт.

Обсяг: усі тести в server/ і web/ (старі для US-01–US-04 і нові з prompts/6.2), Gherkin-сценарії реалізованих історій
US-01…US-12, US-14…US-16, docs/testing-strategy.md, журнали в docs/testing-report.md.

1. Покриття. Таблиця «Gherkin-сценарій → тест (файл, ім'я) / вручну / НЕ покрито».
2. Слабкі тести, з файлом і рядком: порушення правил з docs/testing-strategy.md і кроку 4 скіла .claude/skills/tests-from-ac.
   Перевір і старі тести US-01–US-04, які писалися до цих правил: напр. `<-sub.Updates` без тайм-ауту
   в server/internal/room/service_test.go (зависне замість упасти), ігноровані помилки `s.Join(...)` там само
   і `json.Decode` у TestPreview (server/internal/httpapi/rooms_test.go).
   Окремо — налаштування, через які порожній запуск зелений (--passWithNoTests тощо).
3. Пропущені граничні випадки, яких немає в AC, але які випливають з docs/api.md і docs/data-model.md.
   Перевір щонайменше: place_tile на зайняту клітинку; rotation поза {0, 90, 180, 270}; повторний start_game;
   будь-яка дія після FINISHED чи ABANDONED; place_tile у фазі PLACE_MEEPLE; повідомлення з невідомим type;
   останній тайл стопки, який нікуди не лягає (US-21 «Останній тайл скинуто»).
4. Динамічні перевірки — покажи вивід:
   go -C server vet ./...
   go -C server test -race -count=1 ./...      (на Linux працює, потрібен gcc)
   go -C server test -cover ./...
   Окремо зверни увагу на гонки між snapshot() і зміною Game.
5. Результат — пріоритезований список з мітками [баг] (код поводиться не за вимогами), [слабкий тест], [прогалина].
   Для кожного пункту — як відтворити. Кожен пункт посилається на рядок коду або вивід команди; нічого не вигадуй.
```

## Промпт 2. Виправлення (повторюється для багів з ручної перевірки)

```text
Виправ усі [баг] і [слабкий тест] зі списку аудиту. [прогалина] виправляй, лише якщо вона в межах MVP (docs/requirements.md §2);
решту познач у звіті як відкладене з причиною.
<Для багу з ручної перевірки замість цього: «Баг з ручної перевірки: кроки, очікувано, фактично».>

Для кожного [баг]:
1. тест, що відтворює баг (якщо ще немає) → покажи червоний вивід;
2. виправлення коду → зелений вивід.
Для кожного [слабкий тест]: посиль тест і доведи прийомом «зламай код навмисно», що тепер він падає.

Червоні тести з 6.2 і очікувані значення з вимог не змінюй — лагодь код. Якщо вважаєш, що помиляються самі вимоги, — зупинись і спитай.
Кожне виправлення — окремий коміт `fix(US-XX): …` (AGENTS.md §6).
Допиши в docs/testing-report.md → «Журнал: знайдені баги»: причина, виправлення, регресійний тест, коміт.
```

## Промпт 3. Ручний smoke-чекліст

```text
Склади ручний smoke-чекліст інтерфейсу в docs/testing-report.md, розділ «2. Ручний чекліст»:
таблиця «№ | Крок | Очікувано | Результат | Примітка», 15–25 кроків. Колонки «Результат» і «Примітка» залиш порожніми — їх заповню я.

Покрий усе, що в docs/testing-strategy.md і в матриці 6.2 позначено «вручну», плюс один наскрізний прохід
від створення кімнати до кількох ходів у двох вікнах і закриття вкладки під час партії.
Кожен крок — одна дія й спостережуваний результат. Тексти повідомлень — дослівно з AC.
```

> Чекліст проходимо **самі**. Знайдене — у Промпт 2 з описом кроків.

## Промпт 4. Звіт

```text
Заверши docs/testing-report.md. Я пройшов чекліст, результати вже в таблиці. <Або вставити результати.>

Структура:
1. Покриті історії та сценарії: таблиця «історія → сценарій → тест (файл, ім'я) → рівень»; окремо — що перевіряється лише вручну.
2. Ручний чекліст (заповнений).
3. Знайдені баги: 2–3 найсуттєвіші з журналу. Для кожного: симптом → як знайшли (автотест / мутація / -race / ручна перевірка /
   звірка тайлів з коробкою) → причина → виправлення → регресійний тест → коміт.
   Лише реальні випадки з журналу та git log. Якщо реальних менше двох — скажи мені, не добирай.
4. Інженерна рефлексія: де ШІ помилявся чи хитрував під час написання тестів — з аудиту, мутацій, що вижили, і журналу.
   Для кожного: що було → чому це погано → як виправили. Лише реальні випадки з журналу й аудиту.

Журнали перенеси у відповідні розділи або в додаток. Обсяг — до 3 сторінок.
```

## Що закладено в промпти і чому

| Елемент | Навіщо |
|---|---|
| Нова сесія і роль «не писав ні коду, ні тестів» | Агент, який щойно писав тести, схильний вважати їх правильними; окремий рецензент знаходить більше |
| Аудит без змін, окремо від виправлень | Спершу повна картина з мітками [баг] / [слабкий тест] / [прогалина], потім виправлення за чітким правилом; інакше агент «тихо» переписує тести |
| Критерії слабкого тесту — посиланням на стратегію і скіл | Аудит перевіряє ті самі правила, за якими писалися тести; приклад `<-sub.Updates` — реальне місце в старих тестах, написаних до цих правил |
| Пропущені граничні випадки з `api.md`, а не з фантазії | Нові перевірки прив'язані до контракту, скоуп не розширюється |
| `go test -race` на Linux | На Windows він не працював (prompts/5.2); з появою Game гонки між знімком і станом стають реальним ризиком |
| Червоний тест → фікс → зелений, окремий коміт | Видно, що баг справжній і що виправлення його закриває; коміти — доказ для звіту |
| Колонку «Результат» заповнює людина | Ручне тестування за завданням проходимо самі; ШІ не повинен «пройти» чекліст за нас |
| «Лише реальні баги, не добирай» | Без цього ШІ вигадує правдоподібні баги, щоб заповнити розділ звіту |
