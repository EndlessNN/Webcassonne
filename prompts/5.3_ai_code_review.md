# 5.3 AI-рев'ю коду перед злиттям

Рев'ю робить **GitHub Copilot code review** у Pull Request. Правила рев'ю лежать у [`.github/copilot-instructions.md`](../.github/copilot-instructions.md): Copilot читає цей файл автоматично для кожного PR.

## Як запускаємо

1. Відкриваємо PR з `feature/...` у `main`.
2. У правій панелі PR → **Reviewers** → **Copilot** (або коментар `@copilot review`).
3. Copilot залишає коментарі до рядків. На кожен суттєвий коментар:
   - або виправлення окремим комітом `fix(review): …` з посиланням на коментар;
   - або відповідь у треді, чому не виправляємо.
4. Мердж — лише після того, як усі суттєві треди закриті, а перевірки з AGENTS.md §5 проходять.

## Правила рев'ю (зміст `.github/copilot-instructions.md`)

```text
Ти рев'юєш Pull Request у репозиторії Webcassonne. Правила проєкту — у AGENTS.md, контракти — у docs/api.md і docs/data-model.md.
Пиши коментарі українською. Кожен коментар починай з рівня: [блокер], [важливо] або [дрібниця].

Перевір:

1. Відповідність архітектурі
   - Залежності лише в один бік: httpapi → room → game → model; store знає лише model.
   - Сервер — єдине джерело правди: клієнт не валідує ходи й не рахує очки.
   - Шляхи, поля JSON, типи повідомлень і коди помилок збігаються з docs/api.md. Усе, чого немає в контракті, — [блокер].
   - web/src/api/types.ts збігається з docs/api.md поле в поле.

2. Безпека
   - Токени й коди кімнат — лише crypto/rand.
   - Токен гравця і порядок стопки ніколи не потрапляють у відповіді іншим гравцям.
   - Тіла запитів обмежені за розміром; вхідні дані валідуються на сервері.
   - WebSocket перевіряє Origin; токен перевіряється до апгрейду.

3. Обробка помилок і конкурентність
   - Усі помилки — у єдиному форматі {"error":{"code","message","details?"}} і лише з кодами з docs/api.md §1.
   - Немає panic у бізнес-логіці; помилки не ковтаються мовчки.
   - Стан кімнати змінюється лише під м'ютексом; мережевий I/O не виконується під м'ютексом.
   - Горутини й з'єднання закриваються (немає витоків при закритті вкладки).

4. Чистота коду
   - Терміни з глосарію AGENTS.md §6, без синонімів.
   - Немає мертвого коду, зайвих абстракцій і залежностей, не погоджених у ADR.
   - TypeScript без any; React-ефекти прибирають за собою (WebSocket, таймери).

5. Тести
   - Кожен Gherkin-сценарій історій з PR покритий тестом або в описі PR сказано, як він перевірений вручну.
   - Очікувані значення в тестах узяті з docs/requirements.md, а не підігнані під код.

Не коментуй стиль, який виправляє gofmt чи oxlint. Не пропонуй функції поза MVP (акаунти, БД, відновлення після відключення).
```

## Чому так

| Рішення | Навіщо |
|---|---|
| Правила у `.github/copilot-instructions.md`, а не в кожному запиті | Copilot підхоплює їх автоматично; рев'ю однакове для всіх PR і всіх членів команди |
| Рівні [блокер] / [важливо] / [дрібниця] | Видно, що обов'язково виправити до мерджу, а що можна відкласти |
| Посилання на AGENTS.md і контракти замість повторення | Рев'юер перевіряє за тими самими джерелами правди, що й агент, який писав код |
| Чотири блоки з завдання: архітектура, безпека, помилки, чистота | Прямо відповідають вимогам до рев'ю |
| Специфічні для WebSocket пункти (I/O під м'ютексом, витоки горутин) | Найімовірніші приховані баги в мультиплеєрному коді |
| «Не коментуй те, що ловить лінтер» | Менше шуму; детерміновані перевірки вже окремо |
