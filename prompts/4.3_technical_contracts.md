# 4.3 Технічні контракти: модель даних і API

## Фінальна версія промпту

```text
Дій як Backend Tech Lead, який пише контракти, за якими двоє інших розробників (сервер на Go і клієнт на React/TS) працюватимуть паралельно, не питаючи один одного. Усе, чого немає в контракті, не існує.

Проєкт: «Webcassonne» — браузерна мультиплеєрна емуляція базової «Carcassonne».

<архітектурні рішення>
- Go `net/http` + WebSocket, один процес; React + TS.
- Стан лише в пам'яті процесу, БД немає.
- Гості без акаунтів: сервер видає `playerId` (UUID) і секретний `token` при створенні кімнати та вході. Токен передається в query-параметрі WebSocket.
- Після кожної зміни сервер надсилає кожному гравцю повний знімок стану кімнати.
- Сервер — єдине джерело правди: клієнт не валідує ходи й не рахує очки.
</архітектурні рішення>

<технічний аналіз>
[вставити docs/technical-analysis.md: сутності, життєві цикли, заборони, припущення, прогалини]
</технічний аналіз>

<історії MVP і критерії приймання>
[вставити US-01…US-23 з Gherkin-сценаріями з docs/requirements.md]
</історії MVP і критерії приймання>

Створи три розділи:

1. **Модель даних** (окремий документ). Хоча БД немає, опиши логічну схему як таблиці: для кожної сутності — поля, типи, null/not null, первинний ключ, зовнішні ключі, обмеження унікальності (напр. нікнейм унікальний у кімнаті без урахування регістру; одна клітинка поля — один тайл). Окремо: які сутності обчислюються. Окремо: формат статичного каталогу тайлів — як описати сторони, сегменти доріг, міст і полів, щити й межування поля з містами так, щоб на ньому можна було реалізувати стикування і підрахунок полів.

2. **API** (окремий документ):
   - REST-ендпоінти для дій поза грою (перевірка здоров'я, створення кімнати, попередній перегляд кімнати за кодом, вхід у кімнату): метод, шлях, тіло запиту, тіло й код успіху, усі можливі коди помилок.
   - WebSocket: шлях і рукостискання, повідомлення клієнт → сервер (тип, поля, хто й у якій фазі може надсилати), повідомлення сервер → клієнт з повним прикладом знімка стану.
   - Для кожного поля знімка — яка історія його потребує.
   - Що ніколи не потрапляє в знімок.

3. **Єдиний формат помилки** для REST і WebSocket: структура JSON, таблиця кодів (код, HTTP-статус, коли виникає, яка історія).

Правила:
- Кожен ендпоінт, повідомлення і поле має бути потрібне хоча б одній історії MVP. Наприкінці — таблиця «історія → частина контракту». Історії без контракту або контракт без історії — познач.
- Обертання тайла й панорамування поля — локальні дії клієнта; не створюй для них повідомлень.
- Не додавай пагінацію, версіонування, авторизацію через заголовки та інше, що не випливає з історій.
- Поля JSON у camelCase, значення enum ВЕРХНІМ_РЕГІСТРОМ.
- Відповідь українською, markdown, приклади JSON — реалістичні, з нікнеймами «Олег», «Ірина».
```

## Що закладено в промпт і чому

| Елемент промпту | Навіщо |
|---|---|
| Роль «контракт для паралельної роботи», «чого немає в контракті — не існує» | Задає рівень деталізації: типи, коди, приклади, а не загальний опис |
| Архітектурні рішення з ADR як вхід | Контракти мають відповідати вже обраним WebSocket, токенам і знімкам |
| Логічна схема як таблиці, хоча БД немає | Вимога курсу; обмеження унікальності все одно перевіряє код сховища |
| Окремо формат каталогу тайлів | Без нього неможливо реалізувати US-12 і US-22; це найбільша прогалина з 4.1 |
| Поле знімка → історія і таблиця відповідності | Захист від «зайвих» полів і від історій без контракту |
| Явна заборона повідомлень для обертання й панорамування | Модель схильна робити кожну дію UI запитом до сервера |
| Єдиний формат помилки для REST і WS | Клієнт обробляє помилки одним кодом незалежно від транспорту |
| Конвенції імен (camelCase, UPPER enum) | Однакові типи на Go і TS без перетворень |
