# 4.2 Архітектурні рішення (ADR)

## Фінальна версія промпту

```text
Дій як Software Architect, який допомагає студентській команді обрати найпростішу архітектуру, що гарантовано вкладеться в дедлайн. Ти не продаєш модні технології: кожна зайва частина системи — ризик зірваного демо.

Проєкт: «Webcassonne» — браузерна мультиплеєрна емуляція базової «Carcassonne» з автоматичним підрахунком очок.

<обмеження команди>
- 3 людини, один семестр (~12 тижнів розробки), паралельно з іншими курсами.
- Нульовий бюджет: без платних сервісів і хостингу. Демо — локальний запуск на ноутбуці.
- Досвід: React + TypeScript (впевнено), Go (обрано командою, базовий досвід), Java/Spring (з іншого курсу), PostgreSQL і Docker (базово).
- Код значною мірою генерує ШІ, тому важливі строгі типи, поширеність стеку і простота тестування.
- Запуск має бути 1–2 командами з чистого терміналу.
</обмеження команди>

<результат технічного аналізу>
[вставити docs/technical-analysis.md: сутності, життєві цикли, заборони, припущення, прогалини]
</результат технічного аналізу>

<рішення, які команда вже ухвалила>
- Бекенд — Go, фронтенд — React + TypeScript.
- Бази даних немає: акаунтів, історії партій і відновлення після відключення в MVP немає, стан живе лише під час партії.
</рішення, які команда вже ухвалила>

Оформи ADR (формат: Статус, Дата, Контекст, Розглянуті варіанти — таблиця «плюси/мінуси», Рішення, Наслідки) для вузлів:
1. Структура репозиторію (моно чи кілька репозиторіїв; потрібен чи ні монорепо-інструмент).
2. Стек UI, включно з тим, чим малювати ігрове поле, що росте в усі боки (SVG, Canvas, ігровий рушій).
3. Стек бекенду: роутер/фреймворк, як обробляти одночасні дії гравців в одній кімнаті, бібліотека WebSocket.
4. Зберігання даних: обґрунтуй рішення «без БД» проти SQLite, PostgreSQL і Redis чесно, з мінусами. Поясни, як закрити вимогу курсу «сховище підключено» без БД.
5. Ідентифікація гостей і синхронізація стану між гравцями (токени, повні знімки чи дельти, WebSocket чи polling/SSE).

Правила:
- Для кожного вузла — мінімум 3 варіанти, включно з «найпростішим можливим».
- У «Наслідках» — що ми втрачаємо і як дорого буде змінити рішення пізніше.
- Не пропонуй інструменти, яких немає в обмеженнях, якщо вони не дають очевидної переваги для дедлайну.
- Відповідь українською, кожен ADR — окремий markdown-документ з номером 0001, 0002...
```

## Що закладено в промпт і чому

| Елемент промпту | Навіщо |
|---|---|
| Роль «найпростіша архітектура під дедлайн» | Без цього ШІ пропонує мікросервіси, Kubernetes і Redis для гри на 5 людей |
| Реальні обмеження: 3 людини, семестр, нульовий бюджет, досвід | Рішення мають сенс лише відносно ресурсів команди |
| Уже ухвалені рішення (Go, React, без БД) як вхід | Команда вирішила це сама; ШІ має обґрунтувати й зафіксувати наслідки, а не переобирати |
| Вимога чесно порівняти «без БД» з SQLite/PostgreSQL/Redis | Рішення без БД ризиковане для вимоги курсу; потрібні аргументи на рев'ю |
| Окремий вузол «ідентифікація і синхронізація» | Для мультиплеєра це важливіше, ніж вибір БД |
| ≥ 3 варіанти, включно з найпростішим | Захист від підтвердження першої ідеї |
| Фіксований формат ADR | Однаковий вигляд усіх рішень у `docs/adr/` |
