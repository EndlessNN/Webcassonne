# 4.1 Технічний аналіз вимог (Requirements Digest)

## Фінальна версія промпту

```text
Дій як Senior System Analyst, який готує вимоги до передачі в розробку. Твоя задача — не переписати вимоги, а знайти в них усе, що знадобиться інженерам для проєктування даних і API, і показати, чого бракує.

Проєкт: «Webcassonne» — браузерна емуляція базової гри «Carcassonne» (72 тайли, 2–5 гравців, по 7 міплів) з онлайн-мультиплеєром і автоматичним підрахунком очок. Вхід гостем за нікнеймом, без акаунтів. Мережа — лише щасливий сценарій: гравці не оновлюють сторінку, відновлення після відключення немає.

<вимоги>
[вставити повний docs/requirements.md: User Journey, карту історій зі скоупом, US-01…US-23, Gherkin-сценарії]
</вимоги>

Зроби:
1. **Ключові сутності.** Для кожної: назва англійською (вона піде в код), що це, які історії її потребують. Окремо познач сутності, які краще обчислювати, а не зберігати.
2. **Життєві цикли.** Для кожної сутності зі станами — діаграма переходів у ASCII: стани, події-тригери, хто ініціює (гравець чи сервер). Обов'язково: кімната, фази ходу, міпл.
3. **Бізнес-правила і заборони.** Нумерований список «система ніколи не повинна…». Кожне правило має бути перевірюваним і випливати з вимог, а не з твоїх уявлень про гру.
4. **Технічні припущення MVP.** Таблиця «припущення — обґрунтування»: як ідентифікуємо гостей без авторизації, формат ID кімнати й гравця, система координат поля, як клієнт дізнається про зміни, де зберігається стан, що відбувається з кімнатами після гри.
5. **Прогалини.** Таблиця ситуацій, про які вимоги мовчать, але які доведеться обробити в коді (напр. що буде, якщо організатор вийшов з лобі). Для кожної — запропоноване рішення.

Правила:
- Не додавай функціональності, якої немає в MVP (акаунти, відновлення, чат, боти).
- Не вибирай технології (мову, БД, фреймворки) — це наступний крок. Припущення формулюй на рівні поведінки.
- Якщо правило гри неоднозначне, винеси його в прогалини, а не вигадуй.
- Відповідь українською, markdown, таблиці й короткі списки.
```

---

## Що закладено в промпт і чому

| Елемент промпту | Навіщо |
|---|---|
| Роль системного аналітика, «не переписати, а знайти» | Без цього модель переказує вимоги іншими словами |
| Ключові обмеження MVP у самому промпті (гість, щасливий сценарій) | Інакше модель додає стани на кшталт `RECONNECTING` і сутність `User` |
| Назви сутностей англійською | Ці назви одразу йдуть у код і глосарій `AGENTS.md` |
| «Обчислювати чи зберігати» | Об'єкт (дорога, місто) — похідна від поля; збереження його окремо дало б розсинхронізацію |
| Заборони у формі «ніколи не повинна» | Їх легко перенести в тести та інженерні заборони для ШІ |
| Явна вимога знайти прогалини | Саме прогалини (каталог тайлів, вихід організатора, вибір сегмента для міпла) стали джерелом рішень у контрактах |
| Заборона вибирати технології | Аналіз вимог не має підганятися під стек |
