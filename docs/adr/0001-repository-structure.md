# ADR-0001. Структура репозиторію: монорепозиторій `server/` + `web/`

- **Статус:** прийнято
- **Дата:** 2026-10-28

## Контекст

Команда з 3 людей, один семестр, локальний запуск. Сервер і клієнт змінюються разом: зміна протоколу зачіпає обидві сторони. Документація (`docs/`, `prompts/`) — частина здачі курсу і має лежати поруч з кодом.

## Розглянуті варіанти

| Варіант | Плюси | Мінуси |
|---|---|---|
| **Один репозиторій, папки `server/` і `web/`** | Зміна протоколу — один коміт; одне посилання для здачі; ШІ бачить контракти й код разом | Дві екосистеми (Go і npm) в одному дереві |
| Два репозиторії | Незалежні релізи | Синхронізація версій протоколу вручну; дві здачі; ШІ не бачить другої сторони |
| Монорепо з інструментом (Nx, Turborepo) | Кешування, спільні скрипти | Зайва складність для двох проєктів; Nx не знає Go |

## Рішення

Один репозиторій без монорепо-інструментів:

```text
docs/      документація і контракти
prompts/   промпти етапів курсу
server/    Go-модуль (go.mod тут)
web/       React + TypeScript + Vite (package.json тут)
```

Кожна частина збирається своїми стандартними командами. Кореневого `package.json` чи Makefile немає: дві команди з README достатньо.

## Наслідки

- Будь-яка зміна контракту — один коміт: `docs/api.md` + `server/` + `web/`.
- Go-сервер у продакшн-режимі роздає зібраний `web/dist`, тому для демо достатньо одного процесу (ADR-0003).
- Якщо з'являться спільні скрипти, можна додати Makefile без зміни структури.
