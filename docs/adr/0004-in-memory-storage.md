# ADR-0004. Зберігання: лише пам'ять процесу, без бази даних

- **Статус:** прийнято
- **Дата:** 2026-10-28

## Контекст

Що MVP мусить пам'ятати: кімнати, гравців, стан поточної партії — лише поки партія триває (≈ 30–60 хв). Чого MVP **не** має: акаунтів, історії партій, статистики, відновлення після відключення чи перезапуску (усе це Post/Won't у [requirements.md](../requirements.md)). Одна партія — менше 100 КБ стану. Демо — один сервер на ноутбуці.

## Розглянуті варіанти

| Варіант | Плюси | Мінуси |
|---|---|---|
| **Пам'ять процесу (map під м'ютексом)** | Нуль інфраструктури; запуск однією командою; ніякого ORM/міграцій; найшвидший доступ | Перезапуск = втрата всіх кімнат; один інстанс сервера |
| SQLite | Один файл, переживає перезапуск | Нічого з того, що переживає перезапуск, MVP не використовує; ORM і міграції без користі |
| PostgreSQL у Docker | Знайомо; готовність до акаунтів | Docker для демо; схема під дані, що живуть годину |
| Redis | Швидкий, TTL з коробки | Ще один процес; серіалізація стану без потреби |

## Рішення

Стан зберігається в пам'яті Go-процесу в пакеті `server/internal/store` (`store.Memory`). Логічна схема даних (сутності, ключі, обмеження унікальності) описана в [data-model.md](../data-model.md) і реалізується Go-структурами в `server/internal/model`. Обмеження унікальності перевіряє код сховища, а не СУБД.

Перевірка здоров'я `GET /api/health` повідомляє тип сховища і кількість кімнат — це «підключення сховища» в Walking Skeleton.

## Наслідки

- Перезапуск сервера обриває всі партії. Прийнятно: MVP і так не відновлює партії.
- Горизонтальне масштабування неможливе. Прийнятно для демо й тестових партій з друзями.
- Сховище доступне лише через методи `store.Memory`, тому заміна на БД (якщо з'являться акаунти або відновлення) зачепить один пакет. Таке рішення оформлюється новим ADR.
- Кімнати в кінцевих станах видаляються через 1 годину, щоб пам'ять не росла.
