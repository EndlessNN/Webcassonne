# ADR-0005. Ідентифікація гостей токеном і синхронізація повними знімками через WebSocket

- **Статус:** прийнято
- **Дата:** 2026-10-28

## Контекст

US-01/US-03: вхід без реєстрації, лише нікнейм. Серверу все одно треба знати, хто надсилає хід, щоб відхилити дію не в свій хід (US-07). US-04/US-15: зміни видно всім за ≤ 2 с без перезавантаження. Мережа — лише щасливий сценарій; оновлення сторінки не підтримується.

## Розглянуті варіанти

**Ідентифікація**

| Варіант | Плюси | Мінуси |
|---|---|---|
| **Випадковий токен гравця, виданий при create/join** | Нуль реєстрації; не підробити чужий хід | Токен у query-параметрі WS-з'єднання (браузер не дає ставити заголовки) |
| JWT | Стандарт | Без акаунтів і серверів, що не мають спільного стану, переваг немає |
| Без ідентифікації (довіряти `playerId` від клієнта) | Простіше | Будь-хто ходить за іншого |

**Синхронізація**

| Варіант | Плюси | Мінуси |
|---|---|---|
| **WebSocket + повний знімок стану після кожної зміни** | Клієнт не відтворює логіку; неможливо розсинхронізуватися | Більше трафіку (знімок ≈ кілька КБ — неважливо) |
| WebSocket + дельти/події | Менше трафіку | Клієнт мусить застосовувати події правильно; більше багів |
| Polling REST кожну секунду | Найпростіше | Затримки, зайве навантаження, гірший UX |
| Server-Sent Events + REST для дій | Простий транспорт | Два канали замість одного |

## Рішення

- `POST /api/rooms` і `POST /api/rooms/{code}/players` повертають `playerId` і `token` (128 біт, hex). Клієнт тримає токен у пам'яті вкладки.
- Клієнт підключається до `GET /api/rooms/{code}/ws?token=…`. Невідомий токен → відмова. Усі подальші дії — повідомлення в цьому з'єднанні.
- Після кожної зміни сервер надсилає кожному гравцю повідомлення `room_state` з повним знімком (без чужих токенів і порядку стопки).
- Помилки дій приходять тільки автору як повідомлення `error` у єдиному форматі (див. [api.md](../api.md)).

## Наслідки

- Закриття WebSocket = вихід з лобі або перервана партія (`ABANDONED`).
- Токен потрапляє в URL WebSocket. Локально й без HTTPS це прийнятно; при публічному розгортанні треба HTTPS.
- Додати відновлення після відключення пізніше просто: зберегти токен у `sessionStorage` і дозволити повторне підключення з ним. Це окремий ADR.
