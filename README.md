# Webcassonne

Вебзастосунок для онлайн-гри в базову Carcassonne невеликою компанією знайомих: кімната за запрошенням, спільне віртуальне поле, автоматичний підрахунок очок.

📋 **Специфікація вимог:** [docs/requirements.md](docs/requirements.md)

## Запуск

Потрібні Go 1.26+ і Node.js 20+. З кореня репозиторію:

```bash
npm --prefix web install && npm --prefix web run build
go -C server run ./cmd/server
```

Відкрийте http://localhost:8090 — головна сторінка зі створенням кімнати.

**Перевірка:**

```bash
curl http://localhost:8090/api/health
```

Очікувано: `{"status":"ok","storage":{"type":"memory","rooms":0}}`.

**Розробка UI з гарячим перезавантаженням** (сервер має бути запущений): `npm --prefix web run dev`, потім http://localhost:5173.

**Тести й лінтери:** див. розділ [«Тести»](#тести).

Порт змінюється змінною `PORT`. Якщо міняєте порт, оновіть також проксі в `web/vite.config.ts`.

## Як перевірити перший робочий сценарій

Сценарій «зібрати компанію в лобі» (US-01–US-04). Запустіть застосунок командами з розділу «Запуск».

1. Відкрийте http://localhost:8090, введіть нікнейм (напр. `Олег`) і натисніть «Створити кімнату». Відкриється лобі з кодом кімнати, а ви будете позначені як організатор.
2. Натисніть «Скопіювати посилання». З'явиться «Скопійовано». Якщо браузер не дає доступу до буфера обміну, з'явиться поле з посиланням для ручного копіювання.
3. Відкрийте посилання в іншому вікні або браузері (або на іншому комп'ютері в тій самій мережі: `http://<ip>:8090/r/<код>`), введіть нікнейм `Ірина` і натисніть «Приєднатися».
4. У вікні Олега Ірина з'явиться в списку гравців без перезавантаження сторінки.
5. Закрийте вкладку Ірини. Приблизно за 2 секунди вона зникне зі списку в Олега.

Граничні випадки:
- порожній або довший за 20 символів нікнейм — повідомлення під полем;
- нікнейм, уже зайнятий у кімнаті (`олег`) — «Цей нікнейм уже зайнятий у кімнаті»;
- шостий гравець або неіснуючий код (`/r/ZZZZZZ`) — відповідне повідомлення.

Кімнати живуть у пам'яті сервера ([ADR-0004](docs/adr/0004-in-memory-storage.md)). Що зараз зберігається, видно на http://localhost:8090/api/health: поле `storage.rooms` показує кількість кімнат. Після перезапуску сервера кімнати зникають — це свідоме обмеження MVP.

Автотести сценарію: `go -C server test ./...` (пакети `internal/room` і `internal/httpapi`).

## Як перевірити хід (US-05–US-16)

Сценарій «зіграти кілька ходів без міплів» у двох вікнах. Підрахунку очок і міплів ще немає: це наступний інкремент.

1. Як вище, створіть кімнату (`Олег`) і приєднайтеся з другого вікна (`Ірина`). У вікні Ірини — «Очікуємо, поки організатор почне гру». Поки в лобі один гравець, кнопка «Почати гру» в Олега неактивна з підказкою «Потрібно щонайменше 2 гравці».
2. Олег натискає «Почати гру». В обох вікнах — поле зі стартовим тайлом, таблиця гравців у порядку ходу з різними кольорами, 7 міплами й 0 очок, «У стопці: 70».
3. У вікні гравця, чий хід, — «Ваш хід», поточний тайл і жовта підсвітка клітинок; у другому — «Хід: <нікнейм>» без підсвітки.
4. Натисніть «Повернути» або клавішу R: тайл повертається на 90°, підсвітка перераховується.
5. Клацніть підсвічену клітинку: тайл з'являється на полі в обох вікнах, у того, хто ходить, — кнопка «Без міпла». Натисніть її: хід переходить до іншого гравця, «У стопці» зменшується на 1.
6. Клацніть непідсвічену клітинку: тайл не кладеться, з'являється підказка сервера (напр. «Сторони тайлів мають збігатися»).
7. Перетягніть поле мишею: видима область зсувається, тайли лишаються на своїх місцях.
8. Закрийте одне вікно під час партії: приблизно за 2 с у другому — «Партію перервано».

Схематичний вигляд усіх тайлів — `docs/tiles-preview.html` (відкрийте у браузері).

## Тести

Усі автотести однією командою з кореня (Go + Vitest, [ADR-0006](docs/adr/0006-testing-stack.md)); перед першим запуском — `npm --prefix web install`:

```bash
npm test
```

Окремо:

```bash
npm run test:go                     # = go -C server test ./...   — game, room, httpapi
npm run test:web                    # = npm --prefix web test     — Vitest, web/src/game
go -C server test -race ./...       # гонки даних; потрібен gcc (на Windows без gcc — без -race)
go -C server test -cover ./...      # покриття — орієнтир, не ціль
go -C server vet ./... && gofmt -l server && npm --prefix web run lint && npm --prefix web run build
```

Що й на якому рівні перевіряємо, правила тестових даних і прийом «зламай код навмисно» — [docs/testing-strategy.md](docs/testing-strategy.md). Покриття сценаріїв, ручний чекліст, знайдені баги й рефлексія — [docs/testing-report.md](docs/testing-report.md).

## Контекст проєкту

- Навчальний проєкт: команда з 3 студентів, університетський курс про ШІ, термін 3 місяці.
- Проєктні артефакти і код генерує ШІ під керівництвом команди.
- Мета: навчитися і реалістично завершити проєкт у строк. Ринок, монетизація та унікальність не мають значення.
- Проєкт закритий: його бачать лише команда, викладач і друзі на тестових партіях. Публікація не планується.
- Еталон правил: фізична копія базової Carcassonne, яка є в команди. Спірні місця в правилах вирішуються за нею.

## Проблема

- Друзі, які живуть у різних містах, не можуть зібратися за одним столом.
- Поточний обхідний шлях (одна фізична копія + камера + Discord/Zoom) незручний: у решти гравців немає гри, камеру треба тримати, очки рахують вручну.
- Ручний підрахунок очок, особливо за поля наприкінці партії, довгий і схильний до помилок.

---

## Цільовий користувач: «Організатор віддаленого вечора»

Єдиний профіль, під який будується MVP.

- Збирає друзів, які роз'їхалися, на регулярну онлайн-партію.
- Добре знає правила Carcassonne і сам пояснює їх друзям. Тому продукт не навчає правилам.
- Спілкування відбувається в окремому голосовому дзвінку (Discord, Zoom). Тому продукт не має чату чи голосу.
- Сам збирає компанію. Тому продукт не підбирає випадкових суперників.

Що для нього критично:

- кожен запрошений друг може приєднатися без труднощів;
- від запрошення до першого ходу минає мало часу (зараз налаштування забирає до 20 хвилин);
- підрахунок очок правильний.

**Поза фокусом MVP:** новачки, які не знають правил; родини з нетехнічними учасниками; досвідчені гравці, яким потрібні доповнення; змагальні гравці, яким потрібні рейтинг і турніри.

## Межі MVP

### Входить

- Створення кімнати та запрошення гравців.
- Онлайн-мультиплеєр: 2–5 гравців в одній партії.
- Віртуальне поле з однаковим станом гри в усіх гравців.
- Правила лише базової Carcassonne, без доповнень, включно з полями та селянами.
- Автоматичний підрахунок очок під час партії та в кінці, показ фінального результату.

### Не входить

- Відновлення стану гри після відключення гравця або оновлення сторінки.
- Чат і голосовий зв'язок.
- Планування майбутніх ігор.
- Навчальний режим, підказки, пояснення правил.
- Гра з ботом.
- Підбір суперників, рейтинг, турніри, статистика партій.
- Доповнення.
- Спрощений інтерфейс для окремих вікових груп.

## Принципи розробки

1. **Підрахунок очок — найризикованіша частина.** Визначення меж доріг, міст і полів та належності фігурок потребує обходу графа, а саме таку логіку ШІ найчастіше генерує з помилками. Тому підрахунок реалізується як окремий модуль без залежності від інтерфейсу та мережі і покривається модульними тестами до інтеграції в інтерфейс. Тестові ситуації беруться з фізичної гри.
2. **Мережа: спочатку щасливий сценарій.** Усі гравці мають стабільне з'єднання і не оновлюють сторінку. Обробка розривів з'єднання відкладена за межі MVP.
3. **Перевірка з користувачами:** 2–3 тестові партії з друзями і кілька запитань після кожної. Інтерв'ю не проводяться.
